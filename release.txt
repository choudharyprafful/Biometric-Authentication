SecureAI release notes
======================

Release: main at commit 5b3c9ba (16 October 2026); live as API v28 and the web app, deployed
17 October 2026 from that commit.
Live site: https://d2zb1uxt99m5ks.cloudfront.net
First issue: 9 October 2026, for main at commit 5c1970f and the live API v26.

This file lists the bugs and issues left in this release. Section 9 of the document
"SecureAI - Test Planning and Results" lists the same issues with the same IDs; change
both together. IDs starting R- are rows of the risk register,
docs/04_Threat_Model_Risk_Assessment.md, which has the full detail of each.

Fixed since 9 October (2)
-------------------------
Fixed and live.

R-DP-5: The production database's disk was not encrypted, and it had no automated backups or
    deletion protection.
    Fixed: Since 15 October the API uses secureai3, restored from an encrypted copy of a
    snapshot, with deletion protection and daily backups kept for 1 day (the AWS plan refuses
    more).
    Remaining: On 22 October, delete the old unencrypted instance secureai2 (stopped) and the
    two snapshots made for the switch, after Secrets Manager takes over secureai3's master
    password.

R-SC-6: CloudFront forwarded requests to the API over plain HTTP, and the API server also
    accepted direct requests on port 80.
    Fixed: Since 16 October CloudFront connects to the API over HTTPS only (TLS 1.2 or later,
    with a Let's Encrypt certificate on the instance). Port 443 admits only CloudFront, and port
    80 answers only the certificate's renewal check.

Live with API v28 (7)
---------------------
Fixed in this release's code, and live since 17 October 2026 (API v28), after three production
database migrations: email verification, bystander reports and bystander consent requests
(scripts/ops/migrate-*.mjs).

R-AUTH-10: New passwords were not checked against lists of breached passwords.
    Fixed: Sign-up and both reset paths refuse common passwords, passwords found in Have I Been
    Pwned (only the first 5 characters of the hash leave the server), and passwords containing
    the email's name or "SecureAI".
    Remaining: An existing password is checked only when it is next changed.

R-LOG-6: Audit-log messages contained email addresses, including parents' emails for under-18
    accounts.
    Fixed: Messages name the account by id ("user 42"). The email stays in one structured column
    for filtering, and goes with the entry after 12 months.
    Remaining: Entries written before the change keep their text, as the log's hash chain must
    not be edited.

R-PAY-5: Someone could create throwaway accounts to reset the free-tier limits.
    Fixed: Sign-up emails a 24-hour confirmation link; uploads and payments wait for it.
    Remaining: A disposable inbox can still receive the link, so each account costs more but is
    not impossible.

R-SC-8: The API's Content-Security-Policy did not name form-action or base-uri (ZAP, Medium).
    Fixed: Both are set to 'none'; a ZAP rerun reports no Medium or High alert.

R-PRIV-10: Team 2's Bystander Consent Policy was not implemented: people shown in an upload had
    no say (was OTH-4).
    Fixed: The upload asks who else the file shows. Someone with a SecureAI account is asked in
    their own account, and no feature uses the file until all agree. A public page takes reports
    from people shown in a file, for a staff queue.

R-PRIV-11: Withdrawing personalisation stopped the profile but left the files it read in
    storage.
    Fixed: Withdrawing now offers to delete exactly those files.

R-ML-12: The topic profile read only a to z and 0 to 9, so writing in other languages gave few
    or no topics.
    Fixed: Words are found with Unicode word segmentation; a fairness check in CI covers eight
    synthetic writers.
    Remaining: Common words are filtered for English only.

Open issues (1)
---------------
Not yet fixed.

R-AC-6: The production database is still flagged as publicly accessible, although its firewall
    admits only the API.
    Impact: One mistaken firewall rule would expose it to the internet again.
    Plan: Turn public accessibility off and run migrations from inside the network.

Partly fixed (9)
----------------
Fixed in part; the remainder is described.

R-BIO-1: The face liveness check does not stop a replayed video of the person blinking, a mask,
    or well-shaped image noise.
    Impact: Face sign-in is weaker than a passkey or the phone's key.
    Plan: Passkeys and phone keys remain the recommended factors; a cryptographic liveness check
    would need dedicated hardware.

R-AUTH-9: The demo admin password was published on the live sign-in page before the fix and is
    still in the repository's history.
    Impact: Anyone who saw it could sign in as that admin.
    Plan: The project owner changes the demo admin password (left to them because assessors may
    use it).

R-PAY-3: Self-service refunds check the 14-day window and status, but not whether the paid plan
    was used.
    Impact: Someone could use a plan and then refund it within 14 days.
    Plan: Add usage metering if real payments are introduced.

R-ML-10: Face-matching accuracy and fairness across groups of people have not been measured.
    Impact: Face sign-in may work less well for some people; a passkey is always offered
    instead.
    Plan: Measure with a demographically labelled set of consented faces before any real launch.

R-SUPPLY-5: The phone app's build tooling has 42 dependency advisories (re-counted 7 October; 48
    before the first fixes and 30 just after them, before new advisories were published).
    Impact: Risk in the tools that build the app, not in the code the app runs.
    Plan: Remaining fixes need a newer Expo SDK; upgrade before a real release.

R-SUPPLY-2: The phone app is outside the main workspace, so CI does not audit its dependencies
    or build the Android app (the iPhone build runs in ios.yml).
    Impact: A broken Android build or a vulnerable mobile dependency is noticed only when
    someone builds it.
    Plan: Add an Android build and a mobile dependency audit to CI.

R-MOBILE-1: The passkey ceremony on real phones has not been verified.
    Impact: Passkey sign-in in the phone apps may fail on some devices.
    Plan: Verify on Android and iPhone hardware with the site's Digital Asset Links and
    associated domains.

R-MOBILE-4: On iPhone, the sign-in key is an RSA-2048 key in the Keychain, not in the Secure
    Enclave (which holds only P-256 keys).
    Impact: The key is protected by the Keychain and biometrics, but not by the Secure Enclave
    hardware.
    Plan: Move to a P-256 key in the Secure Enclave, with the server's verification updated to
    match.

R-MOBILE-6: The phone app's checks for a rooted or jailbroken phone run on the phone, which can
    hide root from them. Phone builds made from main check for root, jailbreak and (in release
    builds) an emulator, and the API then refuses a new phone key; Android release builds are
    obfuscated with R8.
    Impact: A rooted phone that hides it is treated as a normal phone, and the server can't
    verify what the phone reports.
    Plan: Play Integrity (Android) and App Attest (iOS), which the server can verify.

Accepted limitations (7)
------------------------
Known and accepted for this proof of concept, with the reason recorded in the risk register.

R-AC-4: Administrators can see the audit trail of their own actions.
    Impact: The log is a weaker check on administrators themselves.
    Plan: Accepted by decision; reversing it is a one-line change (routes/security.ts,
    canSeeAuditLogs).

R-SUPPLY-4: One logger release, pino 9.14.0, is installed although it lacks the provenance
    signature of earlier releases.
    Impact: Its contents were reviewed; later pino releases are still checked.
    Plan: Accepted with a scoped exception for exactly that version.

R-LOG-1: The rate limiter, the audit-log write queue and the alert cooldown are held in one
    server's memory.
    Impact: Correct for the single production instance; several instances would need a shared
    store.
    Plan: Use a shared store such as Redis if the API runs on more than one instance.

R-ML-6: Data cannot be removed from a model that has already learned from it.
    Impact: The live models are rebuilt from current data on every request, so withdrawn or
    deleted data stops counting at once; this would not hold for a model trained once and kept.
    Plan: Accepted as stated in the brief: limitations stated, not solved.

R-ADV-1: Adversarial images crafted against the face model are detected, not prevented.
    Impact: A probing pattern raises an alert for staff; the attack itself is not blocked.
    Plan: Passkeys are the backstop; prevention needs anti-spoofing hardware.

R-SC-7: CloudFront still accepts TLS 1.0 and 1.1 from visitors.
    Impact: Old clients can connect with outdated protocols; current browsers and phones use TLS
    1.2 or 1.3. The hop behind CloudFront is TLS 1.2 or later since R-SC-6.
    Plan: Accepted on 15 October by the project owner, who decided not to buy a domain for the
    proof of concept. For a launch: a domain with an ACM certificate and the TLSv1.2_2021
    policy.

R-PRIV-9: Real biometric data was used in testing: the project owner's own face, on their
    account and one throwaway test account.
    Impact: A deviation from the brief's dummy-data rule.
    Plan: Accepted on 12 October by the project owner: it is their own face, given with consent
    and stored encrypted, and no one else's. Testing since uses synthetic data only.

Other known issues (3)
----------------------
Not risk-register rows. OTH-4 is now R-PRIV-10, fixed and live.

OTH-1: A high-severity advisory in build tooling: source-map-js below 1.2.2
    (GHSA-68fv-2mgg-jv7q), reached through @tailwindcss/vite.
    Impact: Build time only; it is not part of the deployed site.
    Plan: Add an override to 1.2.2, which is now past the 7-day minimum package age.

OTH-2: Differential privacy for the behaviour model is built and tested, but switched off in
    production (BEHAVIOR_MODEL_DP_EPSILON is not set).
    Impact: Suggestions are protected by the three-account threshold only.
    Plan: Set the variable once there are enough consenting users: verify:dp shows that at
    epsilon 1 a suggestion needs about 150 of them.

OTH-3: Phone builds made before privacy policy version 2026-10-07.2 cannot acknowledge it.
    Impact: On those builds the policy notice stays until the app is updated.
    Plan: Build and install new phone apps.
